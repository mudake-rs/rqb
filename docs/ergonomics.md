# Ergonomics Compared To Diesel

rqb is not trying to beat Diesel at Diesel's job. Diesel is excellent when a service wants compile-time query typing, schema-coupled models, and multi-backend support.

rqb is optimized for a different service shape:

- Postgres-only applications
- async request handlers
- dynamic search/filter/sort APIs
- server-owned joins, CTEs, raw sources, subqueries, and locks
- serde DTOs instead of Diesel-specific model derives
- straightforward pool-or-transaction execution

The ergonomic win is not that every static query is shorter. Simple reads look similar. The win appears when a query is assembled from optional service input, JSON search requests, nested JSON output, transactions, and write DTOs.

## Schema And Models

Diesel normally starts from `schema.rs` generated by migrations/introspection and Rust models using Diesel derives:

```rust
diesel::table! {
    orders (id) {
        id -> Uuid,
        user_id -> Uuid,
        status -> Text,
        total_cents -> BigInt,
        metadata -> Jsonb,
        created_at -> Timestamptz,
    }
}

#[derive(Queryable, Selectable)]
#[diesel(table_name = orders)]
struct Order {
    id: Uuid,
    user_id: Uuid,
    status: String,
    total_cents: i64,
    metadata: serde_json::Value,
    created_at: DateTime<Utc>,
}

#[derive(Insertable)]
#[diesel(table_name = orders)]
struct NewOrder {
    id: Uuid,
    user_id: Uuid,
    status: String,
    total_cents: i64,
    metadata: serde_json::Value,
}

#[derive(AsChangeset)]
#[diesel(table_name = orders)]
struct OrderPatch {
    status: Option<String>,
    total_cents: Option<i64>,
    metadata: Option<serde_json::Value>,
}
```

rqb uses query metadata plus serde models. The metadata can be generated by `rqb-cli` or written by hand:

```rust
pub const ORDER_STATUS: EnumType = EnumType::new(
    Some("public"),
    "order_status",
    &["draft", "paid", "cancelled", "refunded"],
);

pub const ID: Field = Field::new("id", FieldType::Uuid);
pub const USER_ID: Field = Field::mapped("userId", "user_id", FieldType::Uuid);
pub const STATUS: Field = Field::new("status", FieldType::Enum(ORDER_STATUS));
pub const TOTAL_CENTS: Field = Field::mapped("totalCents", "total_cents", FieldType::BigInt);
pub const METADATA: Field = Field::new("metadata", FieldType::Jsonb)
    .sortable(false)
    .json_paths(JsonPathPolicy::Dynamic);
pub const CREATED_AT: Field = Field::mapped("createdAt", "created_at", FieldType::Timestamptz);

pub fn orders() -> Dataset {
    Dataset::table("orders")
        .fields([ID, USER_ID, STATUS, TOTAL_CENTS, METADATA, CREATED_AT])
        .default_limit(50)
        .max_limit(500)
}
```

Reads need `Deserialize`; writes need `Serialize`. There are no rqb-specific derives:

```rust
#[derive(serde::Serialize, serde::Deserialize)]
#[serde(rename_all = "camelCase")]
struct Order {
    id: Uuid,
    user_id: Uuid,
    status: String,
    total_cents: i64,
    metadata: OrderMetadata,
    created_at: DateTime<Utc>,
}

#[derive(serde::Serialize)]
#[serde(rename_all = "camelCase")]
struct OrderPatch {
    #[serde(skip_serializing_if = "Option::is_none")]
    status: Option<String>,
    #[serde(skip_serializing_if = "Option::is_none")]
    total_cents: Option<i64>,
    #[serde(skip_serializing_if = "Option::is_none")]
    metadata: Option<OrderMetadata>,
}
```

Diesel has improved read ergonomics over time with derives such as `Selectable`, so the honest comparison is not "Diesel cannot be concise". The difference is that rqb uses serde and runtime metadata as the common application boundary, while Diesel uses compile-time query types and Diesel derives.

## Default Projection

Diesel does not force `.select(...)` for normal table reads:

```rust
let rows = orders::table
    .filter(orders::status.eq("paid"))
    .load::<Order>(&mut conn)?;
```

rqb also does not force `.fields(...)`. Omitted fields mean all `selectable` fields from the root dataset:

```rust
let rows = select(orders())
    .filter(STATUS.eq("paid"))
    .fetch_as::<Order>(&db)
    .await?;
```

Use `.fields([...])` when changing the projection:

```rust
let rows = select(orders())
    .fields([ID, STATUS, TOTAL_CENTS])
    .filter(STATUS.eq("paid"))
    .fetch_as::<OrderSummary>(&db)
    .await?;
```

One useful rqb difference: on joins, the default remains the root dataset only. Diesel's default join selection includes both sides, so the loaded type must match the full joined row. rqb keeps joined tables in scope for filters, sort, and explicit projections without widening the response by accident:

```rust
let rows = select(users().alias("u"))
    .left_join(orders().alias("o"), ID.on("u").eq_col(USER_ID.on("o")))
    .filter(STATUS.on("o").eq("paid"))
    .fetch_as::<User>(&db)
    .await?;
```

## Conditional Filters

Dynamic service filters are where Diesel's static type model starts needing boxing or branch-local queries:

```rust
let mut query = orders::table.into_boxed();

if let Some(status) = params.status {
    query = query.filter(orders::status.eq(status));
}

if let Some(min_total) = params.min_total {
    query = query.filter(orders::total_cents.ge(min_total));
}

let rows = query
    .order(orders::created_at.desc())
    .limit(20)
    .load::<Order>(&mut conn)?;
```

rqb keeps one runtime query representation, so optional filters stay local:

```rust
let rows = select(orders())
    .filter_option(params.status, |status| STATUS.eq(status))
    .filter_option(params.min_total, |min_total| TOTAL_CENTS.gte(min_total))
    .order_by(CREATED_AT.desc())
    .limit(20)
    .fetch_as::<Order>(&db)
    .await?;
```

The same pattern works for writes:

```rust
update(orders())
    .set_from(&patch)
    .filter(ID.eq(order_id))
    .filter_option(params.expected_status, |status| STATUS.eq(status))
    .fetch_optional_as::<Order>(&db)
    .await?;
```

## JSON Search API

Diesel is a Rust query DSL. It does not provide a built-in JSON request format that clients can send over HTTP and have validated against a field policy.

rqb treats that as a first-class use case:

```json
{
  "fields": ["id", "status", "totalCents"],
  "sort": [{ "field": "createdAt", "dir": "DESC" }],
  "query": {
    "logical": "and",
    "predicates": [
      { "field": "status", "operator": "equals", "value": "paid" },
      { "field": "metadata.score", "operator": "gte", "value": 80 }
    ]
  },
  "limit": 20,
  "offset": 0
}
```

Server code keeps the trusted shape and merges the client request safely:

```rust
let page = select(order_search_view())
    .filter(ORGANIZATION_ID.eq(current_org_id))
    .request(request)
    .page_as::<serde_json::Value>(&db)
    .await?;
```

The client can choose fields, filter, sort, and page. It cannot create joins, CTEs, raw SQL, subqueries, aggregates, or transactions. Those stay in Rust:

```rust
let page = select(users().alias("u"))
    .left_join(orders().alias("o"), ID.on("u").eq_col(USER_ID.on("o")))
    .filter(ORGANIZATION_ID.on("u").eq(current_org_id))
    .request(request)
    .page_as::<serde_json::Value>(&db)
    .await?;
```

This is the main niche: Knex-style runtime composition, but with a typed Rust builder for trusted SQL shape and validated JSON for untrusted search input.

## Writes

Diesel write types are explicit and strongly typed:

```rust
#[derive(Insertable)]
#[diesel(table_name = orders)]
struct NewOrder {
    id: Uuid,
    user_id: Uuid,
    status: String,
    total_cents: i64,
}

let order = diesel::insert_into(orders::table)
    .values(&new_order)
    .get_result::<Order>(&mut conn)?;
```

rqb maps any `Serialize` value through dataset metadata:

```rust
let order = insert(orders())
    .value(&new_order)
    .fetch_one_as::<Order>(&db)
    .await?;
```

`fetch_*` write methods return all selectable fields by default. Narrow it only when needed:

```rust
let id = insert(orders())
    .value(&new_order)
    .returning([ID])
    .fetch_one_as::<OrderId>(&db)
    .await?;
```

Partial updates use serde's normal field skipping instead of a Diesel-specific changeset derive:

```rust
#[derive(serde::Serialize)]
#[serde(rename_all = "camelCase")]
struct PatchOrder {
    #[serde(skip_serializing_if = "Option::is_none")]
    status: Option<String>,
    #[serde(skip_serializing_if = "Option::is_none")]
    metadata: Option<OrderMetadata>,
}

let order = update(orders())
    .set_from(&patch)
    .filter(ID.eq(order_id))
    .fetch_one_as::<Order>(&db)
    .await?;
```

Upsert stays fluent:

```rust
let order = insert(orders())
    .value(&new_order)
    .on_conflict(ID)
    .do_update([STATUS, METADATA])
    .fetch_one_as::<Order>(&db)
    .await?;
```

## Transactions And Executors

Diesel's sync connection API takes `&mut Conn` and uses transaction closures:

```rust
conn.transaction(|conn| {
    diesel::insert_into(orders::table).values(&order).execute(conn)?;
    diesel::insert_into(order_items::table).values(&items).execute(conn)?;
    Ok(())
})?;
```

rqb's primary style is linear async code:

```rust
let tx = db.begin().await?;

insert(orders()).value(&order).execute(&tx).await?;
insert(order_items()).values(&items).execute(&tx).await?;

tx.commit().await?;
```

Services can accept any executor:

```rust
pub async fn create_order(exec: &impl PgExecutor, order: NewOrder) -> rqb::postgres::Result<Order> {
    insert(orders())
        .value(&order)
        .fetch_one_as::<Order>(exec)
        .await
}
```

The caller chooses the boundary:

```rust
// One-shot query through the pool.
let order = create_order(&db, new_order).await?;

// Same service call inside an explicit transaction.
let tx = db.begin().await?;
let order = create_order(&tx, new_order).await?;
tx.commit().await?;
```

Closure transactions still exist for cases where that reads better:

```rust
db.transaction(txn!(|tx| {
    create_order(tx, new_order).await?;
    audit_order(tx, order_id).await?;
    Ok(())
}))
.await?;
```

## JSONB

Diesel has PostgreSQL JSONB operators such as `has_key`, `has_any_key`, `has_all_keys`, `contains`, and related methods. The rqb advantage is not "Diesel has no JSONB"; it is that JSONB paths participate in the same field metadata and JSON request validation pipeline:

```rust
let rows = select(orders())
    .filter(METADATA.path("campaign").eq("spring"))
    .filter(METADATA.path("score").gte(80))
    .filter(METADATA.key_exists("gift"))
    .fetch_as::<Order>(&db)
    .await?;
```

The same predicates can be accepted from a JSON `SearchRequest` if the field allows dynamic JSON paths:

```json
{
  "query": {
    "predicates": [
      { "field": "metadata.campaign", "operator": "equals", "value": "spring" },
      { "field": "metadata.score", "operator": "gte", "value": 80 }
    ]
  }
}
```

Reads deserialize through serde, so nested JSON can become a normal Rust type:

```rust
#[derive(serde::Deserialize)]
#[serde(rename_all = "camelCase")]
struct Order {
    id: Uuid,
    metadata: OrderMetadata,
}

#[derive(serde::Deserialize)]
#[serde(rename_all = "camelCase")]
struct OrderMetadata {
    campaign: Option<String>,
    gift: bool,
}
```

## Nested Output

Diesel can express many joins, but nested JSON API responses commonly push you toward manual mapping, N+1 loading, or raw SQL with `jsonb_agg/jsonb_build_object`.

rqb gives the common Postgres JSON aggregation shape a builder API:

```rust
#[derive(serde::Deserialize)]
#[serde(rename_all = "camelCase")]
struct UserWithOrders {
    id: Uuid,
    email: String,
    orders: Vec<OrderSummary>,
}

#[derive(serde::Deserialize)]
#[serde(rename_all = "camelCase")]
struct OrderSummary {
    id: Uuid,
    status: String,
}

let user = select(users().alias("u"))
    .left_join(orders().alias("o"), USER_ID.on("o").eq_col(ID.on("u")))
    .fields([ID.on("u"), EMAIL.on("u")])
    .json_agg("orders", [ORDER_ID.on("o"), STATUS.on("o")])
    .filter_agg("orders", ORDER_ID.on("o").is_not_null())
    .fetch_one_as::<UserWithOrders>(&db)
    .await?;
```

`json_agg` returns `[]` instead of `null`, which matches API DTOs better. Use `json_agg_nullable` when `NULL` is the intended result.

## Server-Owned Advanced SQL

rqb lets the server build advanced SQL shapes and then apply normal filters or a JSON request on top.

CTE:

```rust
let recent = cte(
    "recent_orders",
    select(orders())
        .fields([ID, USER_ID, STATUS, CREATED_AT])
        .filter(CREATED_AT.gte(cutoff))
        .build(),
);

let rows = select(Dataset::cte("recent_orders").fields([ID, USER_ID, STATUS, CREATED_AT]))
    .cte(recent)
    .filter(STATUS.eq("paid"))
    .fetch_as::<Order>(&db)
    .await?;
```

Correlated `EXISTS`:

```rust
let rows = select(orders().alias("o"))
    .filter(exists(
        select(events().alias("e")).filter(all([
            EVENT_ORDER_ID.on("e").eq_col(ID.on("o")),
            EVENT_TYPE.on("e").eq("paid"),
        ])),
    ))
    .fetch_as::<Order>(&db)
    .await?;
```

Raw source with safe outer filtering:

```rust
let source = Dataset::raw(
    "SELECT id, user_id, status, total_cents FROM orders WHERE total_cents > 10000",
    "expensive_orders",
)
.fields([ID, USER_ID, STATUS, TOTAL_CENTS]);

let rows = select(source)
    .request(request)
    .fetch_as::<serde_json::Value>(&db)
    .await?;
```

The raw SQL remains server-owned. The request still only sees metadata-approved fields and operators. `Dataset::raw` is a static source; use bindable `raw("... ? ...").bind(value)` fragments in filters, assignments, or CTE bodies when the raw SQL needs parameters.

## Pagination And Debugging

Diesel has rich query construction, but page-plus-count is normally an application helper. rqb has it as a built-in execution path:

```rust
let page = select(orders())
    .filter(STATUS.eq("paid"))
    .order_by(CREATED_AT.desc())
    .limit(20)
    .offset(40)
    .page_as::<Order>(&db)
    .await?;

assert_eq!(page.limit, 20);
assert_eq!(page.offset, 40);
```

Generated SQL can be inspected before execution:

```rust
let built = select(orders())
    .filter(STATUS.eq("paid"))
    .limit(20)
    .build_pg()?;

tracing::debug!("{}", built.rows.debug_sql());
tracing::debug!("{}", built.count.debug_sql());
```

`debug_sql()` prints SQL and `Value` params for diagnostics. Execution still uses bind parameters.

## Error Mapping

rqb flattens common Postgres errors and gives small helpers for application mapping:

```rust
insert(users())
    .value(&new_user)
    .fetch_one_as::<User>(&db)
    .await
    .on_constraint("users_email_key", |_| AppError::EmailTaken)?;
```

That keeps duplicate-key handling close to the write without a wide match over driver-specific error internals.

## Summary

| Area | Diesel | rqb |
| --- | --- | --- |
| Static CRUD | Excellent, compile-time checked | Simple, runtime checked |
| Default select | Yes, table reads select all columns | Yes, root dataset selectable fields |
| Default join projection | All columns from joined sides | Root dataset only |
| Dynamic optional filters | Usually `into_boxed()` or branching | `filter_option`, one runtime query type |
| JSON search request | Not a built-in concept | Built-in `SearchRequest` with validation |
| Write DTOs | Diesel derives such as `Insertable`, `AsChangeset` | serde `Serialize` |
| Read DTOs | Diesel derives such as `Queryable`, `Selectable` | serde `Deserialize` |
| JSONB | Strong Postgres operator support | JSONB plus path policy and JSON request validation |
| Nested JSON output | Possible, often custom/raw mapping | `json_agg`, serde DTOs |
| Transactions | Closure API over `&mut Conn` | async begin/commit, closure API also available |
| Execution target | Connection-oriented | one `PgExecutor` trait for client, pool, tx |
| Backend support | PostgreSQL, MySQL, SQLite | PostgreSQL only |
| Compile-time SQL safety | Strong | Intentionally weaker |

## Where Diesel Is Still Better

Use Diesel when compile-time query validation is the primary requirement.

Use Diesel when the project needs SQLite or MySQL support.

Use Diesel when the team wants Diesel's migration workflow, associations, derives, and ecosystem.

Use Diesel when complex analytical SQL should stay in a compile-time DSL. Diesel 2.3 added window function support; rqb currently expects raw SQL for many window-function-heavy queries.

Use rqb when the hard part is not one static query, but exposing safe dynamic search over server-owned Postgres query shapes.
